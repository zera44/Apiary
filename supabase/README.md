# Сервер Vulyk (Supabase)

Тут усе, що потрібно серверу: таблиці й правила доступу (`migrations/`),
функція перевірки нічних копій (`functions/backup-commit/`) і перевірки без
Supabase (`tests/`).

Проєктів **два** — однакових:

| Проєкт | Для чого | Секрети GitHub |
|---|---|---|
| `vulyk-test` | тестові збірки гілок (пре-релізи) | `SUPABASE_URL_TEST`, `SUPABASE_ANON_KEY_TEST` |
| `vulyk-prod` | реліз із `main` (Google Play) | `SUPABASE_URL_PROD`, `SUPABASE_ANON_KEY_PROD` |

Так випробування нових версій ніколи не чіпають справжніх даних.

## Що на сервері

* **Дані** — ті самі таблиці, що на телефоні (пасіки, вулики, огляди,
  нотатки, QR-коди, довідники, склад, фінанси, групи «Конструктора»). У
  кожному рядку є власник, версія схеми застосунку, час сервера, номер
  зміни й транзакція. Телефон забирає зміни функцією `sync_pull` за
  курсором і лише із завершених транзакцій, тож жодна зміна не
  «проскочить».
* **Хто що бачить** (перевіряє сама база, Row Level Security):
  * власник — усе своє;
  * помічник — пасіки, до яких запросили (або всі), їхні вулики, огляди,
    нотатки й QR-коди; характеристики, мітки, шаблони й групи власника.
    Може робити огляди й нотатки, переставляти вулики, додавати
    характеристики. Не може змінювати саму пасіку чи шаблони;
  * склад і фінанси власника — лише помічник із дозволом «Також склад і
    фінанси» (тоді може й змінювати);
  * сторонні й запити без входу — нічого.
* **Правила запису**:
  * видалити назовсім із телефона не можна, лише позначкою «видалено»;
  * давніша зміна не «воскрешає» видалене (а позначку «видалено» сервер
    розсилає заново);
  * рухи складу й історія значень лише дописуються (суть запису — товар,
    кількість, значення, час — не змінити; позначки й дату — можна);
  * запис не перенести до чужої пасіки; пасіку запису вулика сервер бере з
    самого вулика (помічник однієї пасіки не допише у вулик іншої);
  * власника рядка не змінити.
* **Запрошення** — за поштою Google. Відправника сервер бере з входу (не
  підробити). Запросити можна лише до своїх пасік. Прийняти може лише той,
  кому надіслано; повторне запрошення оновлює наявного помічника, а не
  дублює його.
* **Сховище файлів**:
  * `stock-photos/<власник>/<назва>.webp` — фото складу (як склад: власник і
    помічник із дозволом);
  * `backups/<користувач>/<id>.db.gz` — нічні копії, лише свої. З телефона
    їх можна тільки додати, не перезаписати й не видалити.
* **Нічні копії** — сервер тримає **2 цілі** на користувача. Нову спершу
  перевіряє функція `backup-commit`: розмір, SHA-256, gzip, база SQLite
  повної довжини. Лише після цього вона видаляє найстарішу. Зіпсовану
  видаляє, а старі не чіпає.
* **Обслуговування**:
  * `ping()` — для keep-alive;
  * щоночі `purge_tombstones()` стирає позначки «видалено», старші за 180
    днів (потрібен pg_cron);
  * видалення акаунта стирає всі дані користувача.

## Створення проєкту (кожен із двох)

1. **Проєкт.** [supabase.com](https://supabase.com) → *New project*:
   * назва `vulyk-test` (потім так само `vulyk-prod`);
   * регіон *Central EU (Frankfurt)*;
   * надійний пароль бази — збережіть у менеджері паролів.
2. **Розклад прибирання.** *Database → Extensions* (або *Integrations →
   Cron*) → увімкнути **pg_cron**.
3. **Таблиці й правила.** *SQL Editor* → *New query* → по черзі вставити
   вміст кожного файлу з `migrations/` (за назвою, від меншого номера) →
   *Run*.
   * `20261010000100_schema.sql` — таблиці;
   * `20261010000200_rules.sql` — правила запису й доступу;
   * `20261010000300_sharing.sql` — запрошення й помічники;
   * `20261010000400_storage.sql` — фото, копії;
   * `20261010000500_maintenance.sql` — пінг, прибирання;
   * `20261010000600_sync.sql` — забирання змін.

   Файли можна запускати повторно — нічого не зламається. Нові міграції
   (наступні етапи) додаються новими файлами; запускати лише їх.
4. **Вхід Google.** *Authentication → Sign In / Providers → Google* →
   увімкнути:
   * *Client ID* — **Web** client ID з Google Cloud (див.
     `docs/REMINDERS.md`, п. 2);
   * *Client Secret* — його секрет;
   * *Authorized Client IDs* — той самий Web client ID (вхід із телефона
     через Google ID-токен);
   * *Skip nonce check* — увімкнути, лише якщо вхід із телефона падає з
     помилкою про nonce.
5. **Функції.** *Edge Functions → Deploy a new function → Via Editor* — дві
   функції, кожна під своєю назвою, *Verify JWT* лишити увімкненим:
   * `backup-commit` — вміст `functions/backup-commit/index.ts` (перевірка
     нічних копій);
   * `delete-account` — вміст `functions/delete-account/index.ts`
     («Видалити акаунт і всі дані»: файли, запрошення, акаунт; решту рядків
     база видаляє разом з акаунтом).

   Або з комп'ютера:
   ```
   npx supabase functions deploy backup-commit --project-ref <ref>
   npx supabase functions deploy delete-account --project-ref <ref>
   ```
   (`<ref>` — частина адреси `https://<ref>.supabase.co`).
6. **Ключі для застосунку.** *Project Settings → API Keys*:
   * адреса проєкту `https://<ref>.supabase.co` → секрет
     `SUPABASE_URL_TEST` (або `_PROD`);
   * публічний ключ — *Publishable key* (`sb_publishable_…`) або
     *anon / Legacy* → секрет `SUPABASE_ANON_KEY_TEST` (або `_PROD`).

   Ключ **service_role / secret** нікуди не копіювати — він обходить усі
   правила.

   Секрети: GitHub → репозиторій → *Settings → Secrets and variables →
   Actions → New repository secret*.

## Keep-alive

Безкоштовний проєкт призупиняється після тижня без запитів. Workflow
`.github/workflows/supabase-keepalive.yml` раз на 3 дні викликає `ping()` в
обох проєктах. Це справжній запис у базу. Проєкт без секретів
пропускається.

GitHub виконує розклад **лише з гілки `main`**, тож keep-alive запрацює
після злиття в `main`. Вручну: *Actions → Supabase keep-alive → Run
workflow*. Якщо проєкт усе ж призупинився — *Restore project* у панелі
Supabase (дані зберігаються 90 днів).

## Перевірка без Supabase

```
supabase/tests/run.sh
```

Скрипт піднімає тимчасову PostgreSQL із заглушками Supabase (`stubs.sql`).
Він застосовує міграції двічі й проганяє `tests/*.test.sql`. Тести від
імені трьох людей перевіряють, хто що бачить і може змінити, запрошення,
правила синхронізації, сховище й прибирання.

Функції перевіряє `node --test supabase/tests/*.test.ts` (Node 22+): копій —
на справжній базі SQLite, видалення акаунта — на фейковому сервері. На GitHub усе це
запускає workflow `Supabase` при кожній зміні в `supabase/`.

## Обмеження безкоштовного тарифу

* база — 500 МБ;
* файли — 1 ГБ;
* один файл — до 50 МБ (копія бази стиснена; фото складу — до 5 МБ, а
  зазвичай 30–80 КБ).

Supabase сам копій бази на безкоштовному тарифі не робить — див.
`docs/REMINDERS.md`, п. 1.
